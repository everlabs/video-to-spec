# Video to Spec

Decomposes a screen-recording walkthrough into per-task user-story specs with the relevant frames embedded inline. The output is meant to be the upstream artifact for later implementation work – one folder of self-contained, reviewable spec items per video.

## When to use

User-facing triggers:
- "video to spec" / "convert this video into a spec"
- "process my loom feedback"
- "decompose this video into tasks"
- "extract todos from this walkthrough"
- "turn this recording into specs"

## Inputs

Required:
- **Video file(s)** – `.mp4`, `.mov`, `.webm` (anything ffmpeg reads).

Optional:
- **Transcript file** – `.srt` or `.vtt` with timestamps. If absent, one is generated (step 3).

Resolution order:
1. If the user passed explicit path(s) in the request, use them.
2. If the user passed a directory, look inside it for video files (+ any matching transcripts).
3. Otherwise **ask**: "Which video(s) should I convert to specs?" Never scan the filesystem for recent recordings or guess on your own – the user always names the input.

If the user gives several videos, run the full workflow once per video, producing one spec folder each.

## Output

Default location: `<cwd>/docs/video-to-spec/<spec>/` where `<spec>` is:

```
<video-stem-slug>--<YYYY-MM-DD>
```

- `<video-stem-slug>` – the video filename stem, lowercase-kebab slugified.
- `<YYYY-MM-DD>` – the video file's modification date (`date -r <video> +%F`), i.e. approximately when it was recorded.

If the folder already exists, ask the user: overwrite it (re-processing the same recording) or create `<spec>--2`.

Final layout:
```
docs/video-to-spec/<spec>/
├── index.md                       summary + open questions
├── transcript.srt                 only when generated by this skill
├── 01-<slug>.md                   one file per task
├── 02-<slug>.md
├── ...
└── frames/
    ├── 00-00-45.png               only frames actually referenced by a task
    ├── 00-01-12.png
    └── ...
```

Intermediate (deleted at the end):
```
docs/video-to-spec/<spec>/_work/
├── timeline.md                    transcript + matched frame per segment
└── frames-all/                    every deduplicated screen state
```

## Workflow

Run these steps in order. Track them as a checklist while you work (use your todo/task-tracking tool if you have one).

Paths like `scripts/transcribe.py` below are relative to this skill's folder – the directory containing this SKILL.md, wherever your agent installed it.

### 1. Resolve inputs

Determine `<video>` (ask if not given – see resolution order above) and `<spec>`. Confirm the resolved `<spec>` name and output path back to the user before continuing.

### 2. Check dependencies

Always needed: `ffmpeg` plus one image-comparison backend (auto-detected, preference order):

| Backend | Detection | Default threshold | Notes |
|---|---|---|---|
| ImageMagick 7 | `magick` on PATH | 200 (PHASH metric) | Preferred. Already installed on most dev machines. |
| ImageMagick 6 | `compare` on PATH | 200 (PHASH metric) | Legacy `compare` binary. |
| Python imagehash | `python3 -c "import imagehash, PIL"` | 5 (hamming, 0–64) | Fallback for systems without ImageMagick. |

Run a quick check:
```bash
which ffmpeg && (which magick || which compare || python3 -c "import imagehash, PIL")
```

If `ffmpeg` is missing: `brew install ffmpeg` (macOS) / distro package manager.

If no comparison backend is present, suggest **one** of:
- `brew install imagemagick` (preferred – general-purpose, no Python pollution)
- `pip3 install --user imagehash Pillow`

Do not auto-install. Transcription dependencies are only checked if step 3 needs them.

### 3. Locate or generate the transcript

**a. Look for provided captions** – in this order:
1. A same-stem sidecar next to the video: `<stem>.srt` or `<stem>.vtt`.
2. A single `.srt`/`.vtt` in the same directory as the video.
3. A transcript path the user mentioned explicitly.

If a `.vtt` is found, convert it (into `_work/`): `ffmpeg -i <captions>.vtt <spec>/_work/captions.srt`.

Found captions → use them and **skip the rest of this step** (no transcription dependencies needed).

**b. No captions → transcribe.** First detect what is available:

```bash
python3 scripts/transcribe.py --detect
```

Providers, in preference order (local first – free and private):

| Provider | Needs | Default model | Notes |
|---|---|---|---|
| `mlx-whisper` | `mlx_whisper` on PATH | `mlx-community/whisper-large-v3-turbo` | Apple Silicon, fast |
| `openai-whisper` | `whisper` on PATH | `turbo` | Any platform |
| `openai-api` | `$OPENAI_API_KEY` (or macOS keychain item `OPENAI_API_KEY`) | `whisper-1` | Paid ~$0.006/min; audio leaves the machine; long files auto-chunked |
| `command` | any user tool | – | `--command 'mytool {audio} -o {srt}'`; placeholders `{video}` `{audio}` `{srt}` |

- **Something available** → tell the user what was detected and which provider you will use. For `openai-api`, state the approximate cost (video duration × $0.006/min) and **confirm before calling** – it is a paid external API.
- **Nothing available** → ask the user to choose (via a structured question tool like AskUserQuestion if available, otherwise in chat): install `mlx-whisper` (Apple Silicon) or `openai-whisper` (any platform), provide an OpenAI API key, supply a custom command template for their own tool, or provide a captions file themselves. Do not auto-install.

Then generate:
```bash
python3 scripts/transcribe.py "<video>" \
    --srt-out "docs/video-to-spec/<spec>/transcript.srt" \
    [--provider P] [--language xx]
```

Pass `--language` only if the user named the spoken language; otherwise let the model auto-detect. The generated `transcript.srt` stays in the spec folder as a final artifact (it was expensive to produce); provided captions stay wherever they were.

### 4. Build the timeline

Run the helper script:
```bash
python3 scripts/process_inputs.py \
    "<video>" "<srt>" "docs/video-to-spec/<spec>"
```

This:
- Extracts one frame per second with ffmpeg.
- Deduplicates via the auto-detected backend (ImageMagick PHASH or Python imagehash) – mouse-cursor drift is ignored, real screen changes are kept. Pass `--threshold N` if too many or too few frames survive (see table above for sensible per-backend ranges).
- Renames kept frames to `HH-MM-SS.png` matching SRT-style timestamps.
- Parses the SRT into segments.
- For each segment, attaches the most recent kept frame within `start + 1s` (a frame change inside the spoken second still attaches).
- Writes `_work/timeline.md` + `_work/frames-all/`.

### 5. Read the timeline

Read `_work/timeline.md` in full. View individual frames from `_work/frames-all/` (read the image files) whenever a segment is ambiguous from text alone – the screenshot is the source of truth for what the user was looking at when they spoke.

### 6. Extract tasks from the timeline

Pass through the timeline identifying candidate tasks. Listen for four kinds of signal:

**Direct tasks** – explicit instructions:
- "we need to ensure…", "let's fix…", "I want…", "this should…", "make it…"

**Reversals** – check the next few segments before locking a task in:
- "wait, actually…", "no, let's not…", "scratch that"
- A later contradictory statement always wins. Drop or rewrite the earlier intent.

**Dissatisfaction** – implied improvements:
- "this is weird", "doesn't make sense", "not useful", "would be better if", "I don't like that…"
- Convert into a task only when you can name the change. If you cannot, log it as an open question.

**Indirect requirements** – observable issues in the matched frame the user is describing but not explicitly requesting. The user navigates through screens and reads what's on them; the implied issue is what's broken/missing/awkward in that screenshot. Always cross-reference the frame, don't infer from text alone.

Group related statements that talk about the same screen / feature into one task. A task can span multiple non-contiguous segments.

### 7. Draft task files

For each task, write `docs/video-to-spec/<spec>/NN-<slug>.md` using this template:

```markdown
# <Short imperative title>

**Type:** <bug | improvement | new feature | question>
**Source segments:** `HH-MM-SS` → `HH-MM-SS` (+ any later references)

## User story
As <role>, I want <capability>, so that <outcome>.

## Motivation
Why this matters. The user pain point or business reason, lifted from what
they actually said – quote them where it's load-bearing.

## Context
Where in the product this lives. Which screen, which role, which flow.
Reference frames inline so the reviewer can see what the user saw:

![<screen description>](frames/HH-MM-SS.png)

## What to do
Concrete changes. Bullet list, scoped tight. If the change touches multiple
files/screens, list each. Don't speculate beyond what the user asked for or
what the frame visibly demands.

## Open questions (optional)
- Anything ambiguous after watching that should be confirmed before
  implementation.
```

Numbering: zero-pad to 2 digits, lowercase-kebab slugs. Order by first appearance in the recording.

For each frame you embed:
- Copy `_work/frames-all/HH-MM-SS.png` → `frames/HH-MM-SS.png` (only those actually referenced).
- Use one to three frames per task – choose the clearest ones, not every match.

### 8. Write the index

Write `docs/video-to-spec/<spec>/index.md`:

```markdown
# Spec: <spec>

Source: `<path/to/video>`
Transcript: provided (`<path/to/captions>`) | generated via <provider> (`transcript.srt`)
Duration: <HH:MM:SS>
Tasks extracted: <N>

## Tasks
1. [<title>](01-<slug>.md) – <one-line summary>
2. [<title>](02-<slug>.md) – <one-line summary>
...

## Open questions
- <Question 1> _(see 03-<slug>.md)_
- <Question 2> _(general)_
```

### 9. Present clarifications as one batch

After everything is drafted, present a single list of clarifying questions covering anything that was ambiguous, contradictory, or where the indirect-requirement reading went beyond what the user explicitly said. Use a structured question tool (e.g. AskUserQuestion, with multiSelect where appropriate) if available, otherwise ask in chat.

Update affected task files based on the answers.

### 10. Offer cleanup

Once the user is satisfied, ask:

> "Source files no longer needed. Delete `<video>`, the source captions (if any), and `<output>/_work/` (intermediate frames + timeline)?"

Wait for confirmation before deleting anything. Never delete the final `docs/video-to-spec/<spec>/` contents (including a generated `transcript.srt`).

## Heuristics and edge cases

- **Long pauses / filler** ("okay", "so", "let me see") – skip; not tasks.
- **Demo actions** the user takes without commentary (typing a test email, clicking around) – only treat as a task if a later segment refers back to it as a problem.
- **Self-corrections** ("oh wait, I see it now") – the corrected statement is the task. The original misread is not.
- **Multiple roles in one recording** (admin then brand then back) – preserve role context in each task; use the "As <role>" field.
- **Frame matches "(none yet)"** – segments before the first kept frame have no anchor. Note this in the task if relevant; usually means the user spoke before sharing screen.
- **Non-English audio** – whisper models handle multilingual audio well; keep the tasks in the language the project's docs use, quoting the speaker verbatim in the original language where load-bearing.
- **Vocabulary discipline** – if the project has a glossary or UI-strings file, prefer those terms in task titles and copy.

## Tone for generated tasks

- Imperative titles ("Require strong password on signup", not "Password validation should be improved").
- Quote the user verbatim when their phrasing captures intent better than your paraphrase.
- No emojis.
- En-dash (–) not em-dash (—).
- Tasks are upstream artifacts – they describe *what* and *why*, not *how*. Implementation details belong in a downstream design doc.
